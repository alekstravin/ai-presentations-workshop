Ты — инженер по эксплуатации. Установи независимый Hermes Agent на моём УЖЕ РАБОТАЮЩЕМ VPS, настрой браузерный доступ по HTTPS и запоминающееся имя через nip.io. Выполни работу и проверки, а не ограничивайся инструкцией.

Входные данные (уточни только недостающие):
- SSH: <существующий SSH alias ИЛИ пользователь@адрес>.
- Префикс имени: <например sever>.
- Разрешённый способ доступа: существующий SSH-ключ/agent; секреты — только скрытым вводом или через приватное хранилище.
- Модель: <провайдер и модель, либо «подключу позже»>.
Не запрашивай пароли и API-ключи обычным сообщением. Не печатай их в логах, истории команд, отчёте или репозитории. Не подключай модель без её реквизитов.

1. Сначала обследуй сервер без изменений: ОС, архитектуру, RAM, диск, текущего пользователя и права, занятые порты, systemd, контейнеры, действующие сайты, reverse proxy, firewall и HTTPS. Найди существующий Hermes, если он есть; не запускай второй экземпляр с теми же данными/портом. Зафиксируй исходный статус сервисов и доступность сайтов. Не выгружай содержимое чужих .env и конфигураций с секретами. Сверь инструкции с актуальной официальной документацией Hermes и nip.io, проверь флаги установленной версии.

2. Сохрани приватные резервные копии только изменяемых конфигураций с владельцами и правами; подготовь точный откат. Если доступна уже настроенная возможность snapshot, используй её в пределах предоставленных прав; не покупай услуги. Не переустанавливай ОС, не меняй шаблон VPS, SSH, DNS других доменов, Docker-сети и правила firewall целиком. Не выполняй dist-upgrade, docker compose down или перезагрузку VPS. Не останавливай и не перезапускай посторонние сервисы. Не обещай абсолютного отсутствия риска: сравни результат с исходным состоянием.

3. Создай отдельного Linux-пользователя hermes без sudo и доступа к Docker socket, если имя свободно. При конфликте выбери отдельное имя и согласованно используй его пути. Установи официальный Hermes от этого пользователя. Проверь происхождение установщика; не используй неподтверждённые скрипты. Пакеты добавляй только необходимые, без массового обновления системы; проверь, не перезапускает ли пакетный менеджер существующие сервисы. При таком риске остановись до изменений и предложи конкретный безопасный вариант.

4. Запусти именно браузерный hermes dashboard, а не только hermes serve. Backend слушает исключительно 127.0.0.1 на свободном порту (9119 — лишь пример). Создай отдельный systemd unit с правильными HOME, PATH, WorkingDirectory, пользователем, автозапуском, журналами и восстановлением после сбоя. Проверь реальный путь CLI. Не смешивай конфигурацию root с профилем hermes. Gateway для Telegram не устанавливай, если я отдельно не попросил.

5. Определи публичный IPv4 VPS и проверь его принадлежность серверу. Преобразуй четыре байта IP в ровно восемь hex-символов с ведущими нулями. Составь имя <префикс>-<hex>.nip.io и проверь DNS снаружи. Пример 203.0.113.10 → cb00710a дан только для документации: не используй его как реальный сервер. Покупать домен или регистрироваться в nip.io не нужно. Укажи, что hex обратим и DNS раскрывает IP: это не анонимизация. При отсутствии IPv4 выбери поддерживаемый nip.io формат IPv6 по документации, не придумывай hex IPv4.

6. Используй УЖЕ РАБОТАЮЩИЙ reverse proxy. Добавь только отдельный virtual host/router для нового имени, не заменяя глобальный конфиг/default и не занимая чужие 80/443. Если прокси нет и порты свободны — установи отдельный подходящий прокси. Если ими владеют Docker/панель/другой сервис, интегрируйся штатным способом либо остановись и объясни конкретный конфликт; не освобождай порты принудительно. Сохрани Host, корректные X-Forwarded-* и поддержку WebSocket. Доверяй только реальным адресам своего прокси, не wildcard-сетям.

7. ДО публикации настрой поддерживаемую авторизацию Hermes. Предпочти официальный OAuth для публичного доступа. Если требуется мой вход или подтверждение OAuth, подготовь конфигурацию и дай безопасный следующий шаг; до завершения оставь backend закрытым. Не подменяй OAuth самодельным отключением проверки входа. Если предлагаешь парольный режим, сначала проверь, допускает ли его актуальная документация для этой схемы; не выдавай LAN/VPN-вариант за рекомендованный публичный. Секрет сессии должен быть постоянным и случайным; секретные файлы — с минимальными правами. Если версия поддерживает хеш пароля, используй его вместо открытого пароля. Не отключай защиту ради успешного запуска.

8. Настрой dashboard.public_url на точный новый HTTPS origin и зарегистрированный OAuth callback на него. Выпусти доверенный сертификат ACME именно для этого имени и проверь автообновление. Выбери доступный challenge без нарушения существующей маршрутизации. Не используй self-signed как готовый результат и не отключай TLS-проверку. При необходимости открытия порта меняй только минимальное правило, сохранив SSH и остальные правила. Проверь конфигурацию proxy до reload; reload разрешён только после успешной проверки. Перезапускай только новую службу Hermes. Старую ссылку перенаправляй лишь если она уже принадлежит этому экземпляру, имеет действующий сертификат и изменение не затрагивает чужой сайт.

9. Проверь фактически:
- systemd active/enabled и запуск от отдельного пользователя;
- backend слушает loopback, не публичный интерфейс;
- DNS нового имени ведёт на VPS;
- HTTPS доверенный, имя сертификата совпадает, обновление настроено;
- без входа закрыты приватные API и WebSocket; публичный /api/status может отвечать и не является доказательством доступа к чату;
- вход, авторизованный API и реальный WebSocket/чат работают;
- если модель подключена — обычный ответ и создание/чтение тестового файла в отдельной папке пользователя hermes;
- после рестарта только службы Hermes и выхода из SSH интерфейс продолжает работать;
- все исходные сайты и сервисы сохраняют прежнюю работоспособность.
Не выдумывай успешный логин, тест с телефона, LLM-ответ или перезагрузку VPS. Отдельно укажи, что проверено автоматически и что ещё требует моего действия. Если модель не задана, напиши «интерфейс настроен, модель не подключена», а не «агент полностью готов».

В конце дай: HTTPS-ссылку; имя пользователя Linux и пути профиля/unit/proxy; команды status, restart и journalctl для этого экземпляра; краткий список изменений и результатов проверок; нерешённые пункты и точный откат. Реквизиты доступа передавай через разрешённое приватное хранилище, без вывода секретов. Для публичной инструкции обезличь IP, hostname, логины и локальные пути. Не публикуй исходный IP даже в hex без отдельного запроса на публикацию адреса.

Действуй самостоятельно в обозначенных пределах. Запрашивай участие только при отсутствии доступа/данных, интерактивной авторизации либо конфликте, который нельзя разрешить без риска для существующих сервисов. Не продолжай опасный шаг по таймауту ожидания ответа.
